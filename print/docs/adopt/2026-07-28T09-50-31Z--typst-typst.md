## Verdict

Worth learning from, in two specific places. The highest-value takeaway is new
information rather than a planned task: **the PDF/UA-1 CI gate is vacuous.**
Both documents it validates (`examples/behoerde.md`, `examples/meeting.md`)
contain zero images, zero tables and zero math — precisely the constructs that
can break PDF/UA-1 — so the gate cannot fail for the three accessibility duties
`internal/assets/templates/behoerde.typ:8` records as still owed, while
`docs/markdown-contract.md:98` already documents alt-text propagation as a
guarantee to users.

Second, the long-recorded "vendor cmarker" task has a confirmed, documented
mechanism upstream (`--package-path` → a data directory checked *before* the
download cache and never written to by the downloader), which turns a Phase-2
roadmap line into a small, well-specified change.

Beyond those, `symprint` is already at or above upstream practice for its size —
pinned action SHAs, least-privilege CI permissions, deterministic fonts,
reproducible output and a typed staged error surface are all in place. Fifteen of
nineteen candidates were rejected.

## What we already do as well or better

- Pinned GitHub Action SHAs → already done throughout `.github/workflows/ci.yml:14`; upstream does the same.
- Least-privilege workflow permissions → `.github/workflows/ci.yml:8` (`contents: read`), matching upstream's `ci.yml:10`.
- Reproducible output via `SOURCE_DATE_EPOCH` → `internal/press/typst.go:172`; upstream exposes the same idea as `--creation-timestamp`.
- Deterministic font resolution → `internal/press/typst.go:143` already passes `--font-path` plus `--ignore-system-fonts`, which is exactly upstream's `FontArgs` contract.
- Engine version pinning in CI → `.github/workflows/ci.yml:72` pins Typst 0.15.0; upstream pins its own toolchain by SHA.
- Typed, staged error surface with actionable hints → `internal/press/errors.go:40` (`RenderError{Stage, Detail, Hint}`) is richer than upstream's flat diagnostic model, and is the right shape for a wrapper.
- Engine-absence handled gracefully rather than fatally → `internal/press/engine.go:60` returns `Available=false` plus an install hint.
- Filesystem sandboxing of the engine → `internal/press/typst.go:131` passes `--root <tempdir>` over a work directory `symprint` fully owns, so untrusted Markdown cannot reach user files. Upstream confines file reads to the root (`crates/typst-kit/src/files.rs:350`) — see Open questions for the symlink caveat.

## Findings

- [ ] **[Architecture] Make the PDF/UA-1 CI gate non-vacuous by exercising the constructs that can break it**
  - **Status quo:** `.github/workflows/ci.yml:78` validates `behoerde` and `meeting` with veraPDF against PDF/A-2a + PDF/UA-1, and the README sells that the profile "fails closed if the document isn't accessible". But `examples/behoerde.md` and `examples/meeting.md` contain 0 images, 0 Markdown tables and 0 math blocks, so the gate passes without ever exercising an accessibility-critical construct. Meanwhile `internal/assets/templates/behoerde.typ:8` records three duties as still owed (image alt text, `table.header` rows, fold/hole marks in `pdf.artifact()`), `docs/markdown-contract.md:98` already promises users that `![alt](image.png)` propagates to Typst's `image(alt:)`, and no test anywhere mentions images. Upstream treats each construct as its own reference test — `tests/ref/pdftags/hashes.txt` contains dedicated entries such as `figure-tags-alt-with-different-lang` and `disable-tags-artifact` — and their accessibility guide states that math without an alt description is a **hard PDF/UA-1 export failure** (`docs/content/guides/accessibility.typ:227`).
  - **Proposed solution:** Pattern adoption. Add a dedicated accessibility fixture (e.g. `examples/` or a test-only document) that contains a Markdown table with a header row, a correct heading hierarchy, an image with alt text, and a math block — then run the existing veraPDF job against it. Expect it to fail initially; that failure is the finding's whole point. Sequence it: tables and heading hierarchy are straightforward today, while the image case likely needs asset-path handling settled first (see Open questions), and the math case is blocked until the Phase-3 `mitex` path lands. Land the parts that can be verified now rather than waiting for all of them.
  - **Effort/Impact:** Low effort for the table/heading portion, medium for the full fixture / high impact. It converts a headline compliance guarantee from asserted to verified, and is fully reversible (the fixture can be dropped without touching product code).

- [ ] **[Architecture] Vendor the cmarker package via `--package-path` to remove the first-render network dependency**
  - **Correction (added during issue planning, 2026-07-28):** this is **lost work, not unbuilt work**. Commit `116c14a` implemented it correctly — vendored files under `internal/assets/packages/preview/cmarker/0.1.9/`, an `assets.MaterializePackages` helper, and both `--package-path` and `--package-cache-path` pointed at the work dir — but it is not an ancestor of `HEAD` and is unreachable from any branch, while issue #6 was closed as completed. The mechanism described below is correct and matches what `116c14a` did; the task is restoration, tracked in #74.
  - **Status quo:** `internal/press/typst.go:20` pins `@preview/cmarker:0.1.9` and notes the engine fetches it over the network on first compile; the same limitation is recorded in `NOTICE:15`, `AGENTS.md:55`, `docs/architecture.md:234` and `docs/architecture.md:271`. This contradicts the README's standalone-binary framing and is a hard blocker for the air-gapped authority environments the `behoerde` profile targets. Upstream resolves packages in a documented order (`crates/typst-kit/src/packages.rs:95`): a **data** directory first, then a download **cache**, then the network — and the downloader only ever writes to the cache, never the data dir. The data directory is selected by `--package-path` / `TYPST_PACKAGE_PATH` (`crates/typst-cli/src/args.rs:454`), wired at `crates/typst-cli/src/packages.rs:7`, with the on-disk layout documented as `<root>/<namespace>/<name>/<version>/` (`crates/typst-kit/src/packages.rs:145`).
  - **Proposed solution:** Code adoption of cmarker (MIT — third-party, already attributed in `NOTICE:15`; note the licence is cmarker's, not Typst's Apache-2.0), pattern adoption from Typst. Embed the cmarker package via `go:embed` alongside the existing templates and fonts in `internal/assets/assets.go`, materialize it into the existing shared cache at `internal/press/typst.go:41` under `packages/preview/cmarker/0.1.9/`, and add one `--package-path <cacheDir>/packages` argument in `internal/press/typst.go:131`. This reuses the materialize-and-symlink machinery already there; no new dependency and no change to the generated `main.typ`.
  - **Effort/Impact:** Medium effort / high impact. Delivers the recorded Phase-2 goal, makes first render hermetic and offline, and pins the supply chain (today the package is fetched and trusted at runtime). Reversible — dropping the flag restores the current download behaviour.

- [ ] **[Architecture] Add hashed reference outputs so silent rendering regressions fail CI**
  - **Status quo:** CI renders all five examples (`.github/workflows/ci.yml:74`) but only checks that the process succeeds and that `behoerde`/`meeting` pass veraPDF. A change to a template in `internal/assets/templates/` that silently alters every rendered page — wrong margin, dropped header, changed heading size — passes CI unnoticed. A repo-wide search found no `sha256`, `hashes`, `golden` or `checksum` usage and no `testdata` directory, so there is no byte-level regression detection at all; `docs/architecture.md:236` already lists "hash-test sample outputs in CI" as a Phase-2 goal. Upstream solves this with hashed references: `tests/ref/pdf/hashes.txt` and `tests/ref/pdftags/hashes.txt` store one 32-byte hash per test, with the documented rationale of catching output changes without committing large binaries (`tests/README.md:100`).
  - **Proposed solution:** Pattern adoption. Add a committed `hashes.txt` mapping each example to the SHA-256 of its rendered PDF, produced with `--reproducible` (which already forces `SOURCE_DATE_EPOCH=0` at `internal/press/typst.go:172`) against the CI-pinned Typst 0.15.0, plus a `make regen-hashes` target for deliberate updates. Note the prerequisite: all five profiles currently default to `Reproducible: false` in `internal/press/profile.go`, so the CI job must pass `--reproducible` explicitly. A hash change on an engine bump is a feature, not brittleness — it forces a conscious review of visual output when Typst is upgraded.
  - **Effort/Impact:** Low effort / medium impact. Reversible; the hash job can be added and removed independently of product code, and the existing render-smoke job stays as-is.

- [ ] **[UX/DX] Use `--diagnostic-format short` for the machine-facing error surfaces**
  - **Status quo:** `internal/press/typst.go:225` (`cleanTypstError`) handles engine failures by truncating raw stderr to 40 lines and passing it through as `RenderError.Detail`. That text is Typst's human format, complete with source-context framing, and it is what the MCP server (`internal/mcp/server.go`) hands back to AI agents and what `--json` embeds — a context-expensive, hard-to-parse blob in exactly the surfaces that need something compact. Upstream ships a second diagnostic renderer for this: `--diagnostic-format short` (`crates/typst-cli/src/args.rs:447`, values at `args.rs:638`) emits one `file:line:col: error: message` line per diagnostic.
  - **Proposed solution:** Pattern adoption. Pass `--diagnostic-format short` when building the argument list in `internal/press/typst.go:131` for the MCP and `--json` paths, keeping the current human format for interactive terminal use. `cleanTypstError` stays as the truncation backstop.
  - **Effort/Impact:** Very low effort / medium impact. A few lines and fully reversible; the smallest of the four findings, included because the MCP server is a headline feature and the cost is near zero.

## Considered and rejected

- **Aggregate "all tests green" job for branch protection** (`.github/workflows/ci.yml:14` upstream) — gate 4 (Worth it): the pattern exists to collapse a large OS/arch matrix into one protection rule; `symprint` has two jobs and no matrix, so it adds a job for nothing.
- **Multi-OS / 32-bit CI matrix** — gate 4 (Worth it): scale fit. `symprint` is CGO-free Go released through `.goreleaser.yml`; cross-compilation is already covered without paying matrix minutes.
- **Fuzz targets for the parser** (`tests/fuzz/`) — gate 4 (Worth it): `internal/press/frontmatter.go` delegates almost all parsing to `gopkg.in/yaml.v3` with `KnownFields`, so a fuzz target would mostly re-fuzz a maintained library. Revisit if hand-rolled parsing grows.
- **`miri` / minimum-version / `cargo doc` jobs** — gate 1 (Transferable): Rust-specific. The Go equivalents (`go vet`, `staticcheck`, `govulncheck`) are already in `.github/workflows/ci.yml:22`.
- **PNG reference-image visual regression** (`tests/ref/`, 1,943 images) — gate 4 (Worth it): 1,943 committed PNGs is the right call for a typesetting engine with thousands of layout tests and the wrong one for five example documents. The hashed-reference variant is the transferable part and is Finding 3.
- **Porting the `pdftags` tag-tree dumper** (`tests/src/pdftags.rs`, 567 lines) — gate 4 (Worth it): it needs a full PDF parser (`hayro_syntax`); reimplementing that in Go to inspect five documents is a large new maintenance surface. The transferable principle — assert accessibility per construct — is folded into Finding 1 via veraPDF instead.
- **`typst init` project scaffolder** — gate 3 (Better): already planned as `symprint init` in `docs/architecture.md:255` with no recorded pain driving it; re-proposing a roadmap item adds no information.
- **`typst watch` incremental preview** — gate 3 (Better): same, already Phase 5 in `docs/architecture.md:254`.
- **`--deps-format json|make` dependency output** (`crates/typst-cli/src/deps.rs`) — gate 3 (Better): `symprint` generates its own fixed input set (`meta.json`, `body.md`, `main.typ`) into a temp dir, so there is no build-system integration that would consume it.
- **`--input key=value` / `sys.inputs` for metadata** — gate 3 (Better): values are strings only, which cannot carry the nested `recipient`/`data` structures; the existing `meta.json` at `internal/press/typst.go:120` is strictly better.
- **`concurrency:` groups to cancel superseded CI runs** — gate 2 (New): not adoptable from this SOURCE; upstream's `ci.yml` has no `concurrency:` block either. Worth doing on its own merits, but it is not a typst finding.
- **Generated documentation website** (`docs/`, `cargo docit`) — gate 4 (Worth it): scale fit. A docs pipeline for a five-profile CLI whose README plus three docs files already cover the surface.
- **PDF Accessibility Checker (PAC) as a second validator** (`docs/content/guides/accessibility.typ:323`) — gate 1 (Transferable): Windows-only freeware GUI with no CI story; veraPDF already covers the automatable checks.
- **`--jobs` compile parallelism** — gate 1 (Transferable): `symprint` renders one document per invocation; there is nothing to parallelize.
- **Test-suite `--- name attr ---` section format** (`tests/suite/`) — gate 3 (Better): a fixture format for thousands of engine tests. Go's table-driven tests in `internal/press/render_test.go` already give equivalent density at this size.

## Open questions

- **Does cmarker actually forward Markdown image alt text to `image(alt:)`?** `docs/markdown-contract.md:98` documents it as a guarantee, `internal/assets/templates/behoerde.typ:8` says it is still owed, and the scope override at `internal/press/typst.go:210` forwards `..args` without naming `alt`. This could not be settled from typst/typst — cmarker lives in `SabrinaJewson/cmarker.typ`. Settled by: reading cmarker's image callback signature, or rendering a fixture with an image and inspecting the resulting tag tree with veraPDF or PAC.
- **Can a local image resolve at all today?** `renderTypst` passes `--root <tempdir>` and writes only `templates/`, `fonts/`, `meta.json`, `body.md` and `main.typ` into it; `cmd/symprint/render.go` copies nothing from the source document's directory. So `![alt](logo.png)` appears to have no resolvable target, which would make the documented syntax in `docs/markdown-contract.md:98` unusable rather than merely untagged. Settled by: one render attempt with a local image. This is a prerequisite for the image half of Finding 1.
- **Root confinement does not survive symlinks.** Upstream states this explicitly at `crates/typst-kit/src/files.rs:350` ("It can still escape via symlinks"), and `symprint` deliberately places symlinks inside its root at `internal/press/typst.go:105`. This is safe today because `symprint` fully controls the work directory, but it constrains any future change that points `--root` at a user-controlled directory — which is one plausible fix for the image-path question above. Worth recording as a design constraint before that change is made.

**Best first step:** add a Markdown table with a header row to `examples/behoerde.md` and watch whether the existing veraPDF job still passes — it is a one-line change that immediately tells you whether the PDF/UA-1 gate has been proving anything.
